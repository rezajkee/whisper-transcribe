# whisper-transcribe

Локальная расшифровка диалога на Mac с разделением голосов, сохранением исходных вариантов и пометками для прослушивания. Обычный `./transcribe.sh запись.m4a` по-прежнему использует WhisperX. Экспериментальный `dual` согласует Parakeet и Nemotron локальной текстовой моделью; на четырёх проверенных пользователем фрагментах он уступил WhisperX по WER. Автоматического переключения режима нет.

## Запуск

Нужны `ffmpeg`, Python 3.12 и подготовленное окружение WhisperX `~/whisper-env`. Для MLX нужен Apple Silicon macOS и отдельное окружение `~/whisper-mlx-env`.

```bash
cd ~/whisper-transcribe
./transcribe.sh запись.m4a --engine whisperx -m medium -n 2 -x 3 --resume
./transcribe.sh запись.m4a --engine dual -n 2 -x 3 --resume
./transcribe.sh запись.m4a --engine parakeet --no-diarize
./transcribe.sh запись.m4a --engine nemotron -n 2 -x 2
./transcribe.sh запись.m4a --engine whisperx -m medium
```

`-l ru` задаёт язык, `-o result` — папку результатов, `-m` меняет только модель Whisper. Рекомендуемая первая команда включает новый последовательный pipeline с WhisperX, возобновлением и автоматическим Markdown. Запуск без `--engine` сохраняет прежний сценарий WhisperX. Все входы, в том числе WAV, конвертируются в отдельную рабочую копию PCM16 / mono / 16 kHz. Исходный файл не перезаписывается.

В `dual` последовательно запускаются Parakeet, Nemotron, одно разделение голосов, Qwen для выбора текстовых вариантов, затем отдельное акустическое выравнивание выбранного текста и назначение спикеров. Каждый тяжёлый процесс завершается до запуска следующего. Это снижает одновременное потребление памяти; не является обещанием максимальной памяти всей машины.

## Подготовка моделей и работа без сети

Обычные запуски работают с локальным кэшем и запрещают загрузки через Hugging Face. Если модели нет, этап завершается ошибкой с сохранением уже готовых результатов. Подготовку выполняйте заранее при доступной сети:

```bash
brew install ffmpeg python@3.12
scripts/setup_mlx.sh --prefetch
```

Скрипт устанавливает полную фиксированную зависимость из `requirements-mlx.txt` в отдельный venv и скачивает полные снимки трёх MLX-моделей. Он отказывается менять `~/whisper-env`. Фиксированы `mlx-audio` commit `f976eab8b47a3cada5aeb3b52a78451ee06117bc`, `mlx==0.32.4`, `mlx-lm==0.32.2`, а также снимки:

- Parakeet: `mlx-community/parakeet-tdt-0.6b-v3`, `ed2b7e8c15f9aaa0b5772e2efb986255eaef7e15`.
- Nemotron: `mlx-community/nemotron-3.5-asr-streaming-0.6b`, `e550040c0478027ed679b2b6b0d055502c103663`.
- Qwen: `mlx-community/Qwen3-4B-Instruct-2507-4bit`, `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`.

WhisperX остаётся в собственном окружении. В проверенной локальной конфигурации используются WhisperX 3.8.6, pyannote.audio 4.0.7, Torch 2.8.0, Transformers 4.57.6. Сначала подготовьте там используемую модель Whisper, HF-модель выравнивания для нужного языка и pyannote. Для нового pipeline русское выравнивание использует `jonatasgrosman/wav2vec2-large-xlsr-53-russian`, английское — `facebook/wav2vec2-base-960h`; `--align-model REPO` задаёт другой заранее кэшированный HF-снимок.

Для существующего pyannote 3.1 нужны принятые условия репозиториев `pyannote/speaker-diarization-3.1`, `pyannote/segmentation-3.0`, `pyannote/wespeaker-voxceleb-resnet34-LM`. Используйте `hf auth login` при подготовке; токен не записывайте в исходники и журналы. Полный кэш должен содержать конфигурацию pipeline и веса обеих зависимостей. Уже подготовленный и проверенный кэш 3.1 можно использовать повторно; переход на community-1 не требуется. Перед отсутствием сети выполните короткий пробный запуск с нужными языком и разделением голосов.

Старые установки pyannote могут безусловно загружать PLDA/community-1. Проверенная 4.0.7 содержит условную загрузку PLDA только для `VBxClustering`; конфигурация 3.1 использует `AgglomerativeClustering` и PLDA не требует. Если старая локальная версия падает на community-1, сначала проверьте установленный код и `WHISPER_DIARIZE_MODEL=pyannote/speaker-diarization-3.1`. Не применяйте дополнительные патчи к работающей версии. Новый worker передаёт waveform в памяти, обходя путь декодирования файла через TorchCodec.

## Словарь и имена спикеров

Словарь — подсказка только для согласования `dual`, не обучение ASR и не разрешение вставлять термины. Для одиночного движка `--glossary` отклоняется. UTF-8 файл может содержать по одному термину в строке или JSON:

```json
{"terms":[{"canonical":"Parakeet","variants":["паракит","паркет"]}]}
```

```bash
./transcribe.sh запись.wav --engine dual --glossary work/terms.json --mapping mappings/meeting.json
./speakers.sh result/ИМЯ.json
./build_dialog.sh result/ИМЯ.json -m mappings/meeting.json
```

Mapping — JSON `{"SPEAKER_00":"Анна","SPEAKER_01":"Игорь"}`; при необходимости `UNKNOWN` тоже можно назвать. Неизвестный или неоднозначный голос остаётся в тексте. Метки относятся к конкретной записи и не гарантируют одну личность между запусками. Перекрытие голосов и ненадёжная смена спикера помечаются для проверки.

## Что сохраняется

Новый pipeline создаёт JSON, TXT, SRT, VTT, TSV и читаемый Markdown. Имена включают безопасное имя исходника, хэш содержимого и движок. Одинаковые имена разных аудио не конфликтуют. Legacy запуск сохраняет привычные имена.

Полные исходные ASR-гипотезы, история этапов, stdout/stderr и измерения процессов находятся в `result/.runs/…/stages/`. `manifest.json` со статусом `complete` — признак завершения всего набора. Частичные результаты не публикуются как готовый транскрипт. В JSON есть исходные фрагменты обеих гипотез, диапазоны символов, настоящие временные опоры декодера, выбор источника и подробный журнал. Отвергнутые варианты также сохраняются. Фрагмент, встречающийся только в одном ASR, остаётся в основном тексте с пометкой.

Различия видны рядом с текстом: время и варианты A/B. Числа, отрицания и термины словаря остаются отмеченными даже после выбора Qwen. Выбор текстовой модели не подтверждён прослушиванием. Модель не получает аудио, не может добавлять слова, менять время или спикера. Она видит одно ограниченное расхождение с соседним контекстом, возвращает только `A`, `B` или `unresolved`. Новые слова, неизвестные/пропущенные ID, повторения ключей, произвольный текст и неверный JSON отклоняются. При неверном ответе сохраняется точный исходный вариант с явной неопределённостью; отсутствие модели или её авария прерывают этап.

Варианты с одинаковыми защищёнными текстовыми элементами обходят этап выбора источника и первоначально выбирают A; различия `C#` / `C`, `.NET` / `NET` или `-5` / `5` считаются расхождением ASR и остаются видимыми даже после выбора. После всех выборов соседние фрагменты объединяются для выравнивания, затем Qwen восстанавливает пунктуацию короткими частями (до 80 символов; не более одного вызова на часть, до 128 выходных токенов) с ограниченным контекстом до и после. Новая конечная точка на искусственной границе отклоняется, если дальше есть выбранный текст, в том числе за границей блока выравнивания; такие случаи помечаются для проверки. Проверка сравнивает защищённые текстовые элементы: слова, значимые символы и их соединение внутри идентификатора. По умолчанию любой символ защищён; небольшой набор обычных знаков предложения (запятая, конечная точка и отдельно стоящее тире) допускается только вне выявленных идентификаторов, числовой записи и неоднозначных операторов. Например, нельзя менять `C#` ↔ `C`, `.NET` ↔ `NET`, `node.js`, адреса с `@`, пути со слешами, внутренние дефисы/апострофы, знаки и разделители чисел; разрыв `C#` → `C #` тоже отклоняется. Все знаки `!` и `?` защищены, включая концы обычных предложений, идентификаторов и положения внутри скобок/кавычек: модель не может добавлять, удалять, переставлять их или менять их соединение с соседним текстом. Такие различия двух ASR считаются расхождением, а попытка изменить знак при исправлении пунктуации сохраняет исходник с отметкой для проверки. Это намеренно ограничивает восстановление вопросительных и восклицательных знаков. Внутри сбалансированных скобок и кавычек весь участок сравнивается буквально: нельзя менять знаки, регистр или пробелы. Так сохраняются `(1,)`, аргументы вызовов, строки и вложенные выражения; запятые между соседними закрытыми выражениями также защищены. Присваивания/отдельные кодовые операторы защищают участок вместе с соседними операндами; компактные выражения и поля `ключ:значение` сохраняют свои разделители. Непарные или перепутанные скобки/кавычки делают локальную часть неоднозначной: модель для неё не вызывается, исходный текст остаётся с отметкой для проверки. Проверка полного соединённого текста и сравнение ASR учитывают защищённые участки через границы частей, включая внутреннюю часть без собственных скобок. Если разбор полного текста неоднозначен, консервативная проверка может откатить исправления на более широком участке. Обычные внешние запятые, конечные точки и регистр вне таких участков по-прежнему можно исправлять. Точки внутри выбранного отрывка защищены даже при пробеле (`node. js`), а точка сразу после числа считается неоднозначной. Символические идентификаторы, в том числе с пробелами вокруг знаков (`C #`, `. NET`), слова с цифрами (`Qwen3`) и подчёркиванием сохраняют регистр; обычные слова допускают посимвольную смену регистра без Unicode-нормализации и расширений вроде `ß` → `ss`. Добавленные, удалённые или перемещённые управляющие символы отклоняются. Знаки чисел сохраняются и при пробелах; изменение отдельных числовых пробелов допустимо только в явно числовой записи. После соединения частей проверяется весь выбранный текст, включая границы блоков; существующие конечные знаки на искусственных границах также защищены, поскольку `node.` / `js` может быть разделённым идентификатором. Неоднозначное изменение, включая многие кавычки, двоеточия или операторы, сохраняет исходную выбранную формулировку с отметкой для ручной проверки. Это консервативная проверка поверхности текста, а не доказательство правильного смысла или пунктуации по аудио. Журнал содержит исходный и итоговый текст, ответ модели, результаты проверки и ссылки на источники. Слишком длинное отдельное слово пропускается с отметкой для проверки. Согласование не удаляет повторы и самоисправления. Стыки независимых окон помечаются как требующие прослушивания: это диагностическая граница, а не доказанное расхождение и не аудиопроверка. Предположение о постоянной задержке Nemotron не применяется.

Пунктуационные изменения принимаются по блокам: каждый предлагаемый блок проверяется вместе с ранее принятыми изменениями на фоне полного исходного текста. Не прошедший проверку блок сохраняется без правки и помечается; остальные могут сохраниться. Итоговый общий защитный контроль остаётся. На сохранённых ответах одного часового прогона такой диагностический повтор сохранил 106 изменений, но их правильность по аудио не проверена. Существующие экспортированные файлы автоматически не обновляются.

Перед экспортом выбранный текст выравнивается по аудио в ограниченных интервалах с дополнительным акустическим контекстом. `timing_source` сообщает реальный источник времени. Если выравнивание пропускает слово или не может надёжно назначить время, текст и варианты остаются, `precise_timing=false`, а таймкод помечается как неподтверждённый. Форматы субтитров всё равно содержат временные интервалы; для точного монтажа такие места нужно проверить вручную.

## Возобновление и настройки

```bash
./transcribe.sh запись.wav --engine dual --resume
./transcribe.sh запись.wav --engine dual --force
cp config.env.example config.env
python3 -m whisper_transcribe --help
```

Возобновление включено по умолчанию. Проверяются хэши входа, артефактов, кода, моделей и окружений. Изменение словаря затрагивает согласование и последующие этапы, mapping — только экспорт. Новые параметры спикеров не требуют повторного ASR. Предыдущие попытки сохраняются; повреждённый или незавершённый этап пересчитывается. `--force` пересчитывает этапы. Работа с одной записью защищена блокировкой.

Полезные параметры: `--chunk-seconds` (до 30), `--overlap-seconds`, `--alignment-padding` (по умолчанию 5 секунд), `--cpu-threads` (по умолчанию 4), `--mlx-venv`, `--whisper-venv`, `--no-diarize`. Пути окружений и обычные параметры можно задать через `config.env` по примеру файла.

## Проверка качества по человеческим эталонам

25 октября 2026 пользователь подтвердил исправление всех четырёх reference по аудио: 10 мин 46 с, 1226 нормализованных слов. WER на tuning / holdout: WhisperX **27,54% / 30,43%**, Parakeet 40,27% / 60,56%, Nemotron 43,47% / 67,70%, dual 42,37% / 61,18%. По этим записям рекомендуем WhisperX; dual остаётся экспериментом. Это оценка слов, а не независимая проверка смысловых ошибок или спикеров. Методика, CER и ограничения — в [отчёте проверки](docs/validation-2026-10-25.md).

В `work/evaluation-20261025/manifest.json` выделены `tuning` и отдельный `holdout`. Файлы `.draft.txt` — черновики ASR. Даже заполненный `.reference.txt` не считается эталоном, пока человек не проверит его по аудио. Инструмент отказывается считать WER/CER при `reference_verified=false` или изменившемся после проверки хэше. Сначала исправьте reference по аудио, сохранив повторы, отрицания и числа; затем **только после подтверждения человеком**:

```bash
python3 -m whisper_transcribe.evaluate mark-verified work/evaluation-20261025/manifest.json \
  --item tune-upk-short --acknowledge-human-review
```

Это явное подтверждение прослушивания, не автоматическая оценка черновика. Повторите отдельно для каждого проверенного файла. Сам код не проверяет качество reference. После любой правки эталона требуется повторное подтверждение.

```bash
python3 -m whisper_transcribe.evaluate score work/evaluation-20261025/manifest.json \
  --split tuning \
  --candidate tune-upk-short=result/UPK-short.json \
  --candidate tune-counters-short=result/counters-short.json \
  --candidate tune-counters-long=result/counters-long.json \
  --output work/evaluation-20261025/parakeet-tuning.json

python3 -m whisper_transcribe.evaluate score work/evaluation-20261025/manifest.json \
  --split holdout --candidate holdout-upk-long=result/UPK-long.json \
  --output work/evaluation-20261025/parakeet-holdout.json
```

Передайте ровно все ID выбранного split, для каждого движка отдельно. Для JSON оценивается только `segments[].text`, без технических пометок и имён. TXT должен быть чистым текстом речи: метки времени, спикеров и заметки автоматически не удаляются. Предпочитайте JSON готового pipeline.

Нормализация: Unicode casefold, последовательности Unicode `\w+`, пунктуация удаляется, пробелы сводятся к одному. WER считается по словам, CER — по тем же нормализованным словам, соединённым одним пробелом; пробел входит в CER. `2`, `два` и `two` различаются; числовые эквивалентности не применяются. Для пустого эталона сохраняются вставки, а WER/CER равны `null` при нулевом знаменателе. Общая оценка суммирует ошибки и длины эталонов, не усредняет проценты файлов. Алгоритм использует линейную память относительно меньшей последовательности; время квадратично, поэтому оценивайте клипы, а не целый час одним эталоном.

Отчёт сохраняет исходные тексты, хэши, ошибки по файлам и агрегаты. Семантической автоматической метрики нет. В item manifest можно добавить `manual_critical_annotations` — список объектов с временем, категорией (`number`, `negation`, `term`, …) и описанием, проверенных человеком. Он переносится в отчёт отдельно от WER/CER. Настройку словаря и правил делайте на tuning; holdout оставляйте для итоговой независимой проверки. Небольшой тест и низкий WER не переключают движок по умолчанию.

## Измерения и ограничения

На коротком локальном 24-секундном фрагменте в этой среде изолированный Nemotron занимал примерно 3.23 с, следующее CPU-выравнивание — 5.97 с; журнал всего пробного запуска — 16.01 с. Это измерения отдельных процессов одного короткого теста, не оценка часа и не SLA. Старые приблизительные часовые оценки не используются для решения о dual. Измерения RAM процесса и MLX-аллокатора перекрываются и не суммируются. Проверенные эталоны уже измерены: dual уступил WhisperX. Длинный проход проверяется отдельно от точности; результаты фиксируются в [отчёте проверки](docs/validation-2026-10-25.md).

Аудио, гипотезы, словари и эталоны могут содержать личные данные. Храните их в игнорируемых `work/` и `result/`; не добавляйте транскрипты в Git. Тесты без моделей: `python3 -m unittest discover -s tests`.

Протокол пунктуации изменил идентичность исходного кода: при повторном запуске кэш согласования и следующих этапов пересчитывается, а результаты ASR и разделения голосов переиспользуются при неизменных входных данных. Предыдущие оценки held-out относятся к результатам старого протокола и не измеряют качество новой пунктуации или нового запуска модели.
